# 全国增值税发票查验平台 — 实战知识库

平台地址：https://inv-veri.chinatax.gov.cn/fpcygzfw/national-invoice-check
技术栈：Vue + TDesign 组件库。以下结论均来自 162 张发票的实战查验（2026-08）。

## 1. 表单结构

表单输入框为 `input.t-input__inner`，按顺序：

| nth | 字段 | 说明 |
|---|---|---|
| 0 | 发票代码 | 数电票**留空**；老式税控票填12位代码 |
| 1 | 发票号码 | 数电票20位；老式票8位 |
| 2 | 开票日期 | **readonly**，不能 fill，必须点日历面板选择 |
| 3 | 金额/校验码 | **动态字段**，见下节 |
| 4 | 验证码 | 填 OCR 识别结果 |

提交按钮：`button` 文本含"查验"。

### 日期选择器（pickDate）
点击 nth(2) 打开面板 `.t-date-picker__panel`：
- 年：`.t-date-picker__header-controller-year input` → 点开选 `.t-select-option`
- 月：`.t-date-picker__header-controller-month input` → 选 `^\d+月$`
- 日：`td.t-date-picker__cell:not(.t-date-picker__cell--additional)` 选 `^日$`（排除相邻月补位格）

## 2. 第4字段的动态规则（关键）

**填入发票代码后，第4字段从"开具金额(不含税)"变为"校验码 后六位"**（TDesign 表单动态切换）。

- **数电票（无发票代码）**：第4字段填**价税合计**（amountTotal）。注意不是不含税金额——首轮曾因此误判"不一致"。
- **老式税控票（有发票代码）**：第4字段必须填**校验码后6位**（印在发票票面右上角）。台账通常没有此列 → 无法自动查验，标记"需补充数据"并请用户提供。
- 诊断方法：`probe_labels.mjs` 可打印填代码前后的表单标签变化。

## 3. 验证码机制

1. 先填好全部表单，再点验证码占位图 `img[style*="cursor"]`。
2. 触发 POST `https://dppt.shanghai.chinatax.gov.cn:8443/fpcy/fpcyyzm/v1/getVerifyCode`，返回 base64 图片写入 img src（`data:` 开头）。
3. 页面提示"请输入验证码图片中的X色文字"，只需输入**指定颜色**的字符（正则：`/验证码图片中\s*的?\s*(黑色|红色|蓝色|绿色|紫色|橙色|黄色|粉色)/`）。
4. OCR 方案：ddddocr + OpenCV HSV 颜色掩码（黑/红/蓝/绿主色，紫/橙/黄备用）+ 外轮廓填充 + 连通域形状过滤。RapidOCR 对此图无效，勿用。
5. **验证码错误有两种表现**：弹窗提示，或**静默刷新验证码图**（无任何 dialog）。提交后需轮询约12秒，检测 img src 变化即视为错误并复用新码重试。

### 验证码不加载的根因（重要）
点击后 src 始终不是 `data:` 开头，多为**表单校验未通过**，最常见原因：
- **数电票"伪发票代码"**：台账把20位号码同时填进了"发票代码"列（code==number）。平台校验失败，验证码接口完全不响应。**识别规则：`code === number && /^\d{20}$/`，应清空 code。**
- 必填字段为空或格式错误。
- 平台限流（见第5节）。

## 4. 结果判定

遍历所有可见 `.t-dialog` 读取文本：
- **一致**：结果弹窗含完整发票详情（购/销方、项目明细），关键词"发票详情/查验结果/当日查验次数"，且无"不一致"字样。
- **不一致**：弹窗/页面含"不一致"。
- **查无此票**：含"查无此票"。
- 限流弹窗含"访问过于频繁"；超次弹窗含"查验次数"。
- 结果弹窗出现后**立即截图**（`page.screenshot`），命名 `{seq}_{发票号码}.png`。

## 5. 限流与速率控制

- 平台限流严格。触发"您的访问过于频繁"后验证码接口会停摆一段时间。
- **必须单 worker 串行**。双 worker 并发20分钟即触发限流。
- 退避策略：限流等60秒；验证码未加载连续3次等45秒；票间隔6-10秒随机。
- 实测安全速率约 0.6-1 张/分钟，162 张全程约需数小时，应后台运行。

## 6. 票种查验能力

| 票种 | 可否查验 | 说明 |
|---|---|---|
| 数电票（普通发票/铁路电子客票等） | ✅ | 无代码，第4字段填价税合计 |
| 增值税电子普通发票（老式税控） | ⚠️ 需校验码 | 有代码，第4字段填校验码后6位 |
| 区块链电子发票 | ❌ | 不接入全国底账库，需在开具地区电子税务局查验 |
| 铁路纸质车票（票号非20位数字） | ❌ | 非增值税发票，不适用本平台 |

## 7. 环境踩坑

- CSV 台账常为 **GBK** 编码（Windows 导出），需 `TextDecoder('gbk')`；部分文件带二进制 TSD 头，表头行需按内容定位。
- Node ESM 下 `NODE_PATH` 无效，用 `createRequire(workspace路径)` 加载 playwright。
- 本环境 python 内置脚本可能报 "source code string cannot contain null bytes"，静态服务改用 Node（serve.mjs）。
- `cv2.imread` 不支持中文路径，用 `np.fromfile + cv2.imdecode`。
- 进程检查勿用 wmic（可能被策略禁用），用 tasklist / 日志时间戳。

## 8. 交付

- 报告为单文件 HTML，截图用相对路径 `screenshots/xxx.png`，须配合 serve.mjs 经 HTTP 预览。
- 按已成功查验数量表述“一致”，同时单列不支持、需补数据和待重试数量。零“不一致/查无此票”不能证明未成功查验的票据为真。

## 9. Windows 批量查验排障与恢复（2026-11-03复盘）

本次132张台账最终为122张平台返回一致、4张区块链票平台不支持、6张缺校验码。首轮111张一致、11张临时失败；追加两轮补验后11张均成功。此案例说明临时失败应补验，不能归为假票；该成功率与次数不保证适用于后续批次。

### 环境安装：模块存在，但浏览器仍缺失

- 初始化曾输出“环境就绪”，运行时却报 `Executable doesn't exist ... chromium_headless_shell-*`。原脚本按固定 `node_modules/playwright/cli.js` 判断并跳过了浏览器安装，且未验证启动。
- 现通过 `createRequire(...).resolve('playwright/package.json')` 所在目录定位 `cli.js`、安装匹配版本 Chromium，并实际启动/关闭 headless 浏览器；失败即停止初始化。`playwright/cli` 子路径未导出，不可直接resolve。安装目录和运行脚本必须加载同一份 Playwright，必要时设置 `PLAYWRIGHT_BASE`。
- 单独修复时在对应 Node workspace 执行 `npx playwright install chromium`，同时下载 matching Chromium/headless shell。不要仅凭 npm 安装成功推断浏览器已就绪。
- Windows 虚拟环境内直接 `pip.exe install --upgrade pip` 曾被拒绝；使用虚拟环境的 `python.exe -m pip ...`。安装失败应保留错误并停止，避免后续误报就绪。
- PowerShell 7 不支持 `Get-Content -Encoding Byte`；确需读原始字节时使用 `Get-Content -AsByteStream`，或交给台账解析脚本检测编码。

### OCR：亮蓝色、细线字形与单字符

- 旧蓝色掩码限制 `V < 240`，会丢掉高亮蓝字；本次截图中可见两个蓝字，但旧掩码计数为0。现蓝色范围为 H=95..140、S>70、V>45（OpenCV HSV），保留V=255。其他颜色阈值按实际截图验证后再改。
- 原尺寸识别为空或长度不符合连通域计数时，对实心掩码及原始颜色掩码分别放大2/3倍，优先选长度与计数一致的候选。连通域计数只是启发式，噪点或字形相连会误计数；不要强行提交错误长度。
- 查验脚本原有 `code.length < 2` 会直接跳过真实的单字符验证码，即使OCR已识别为 `m` 等字符；现允许非空的单字符结果。
- 本次日志出现同一验证码反复12次、或提交后无响应。旧脚本没有强制要求刷新后的src不同于旧src，故“识别失败”也可能是验证码未加载/未刷新，不全是OCR模型失效。连续复用同一src时应检查验证码是否真的更新、页面提示及网络请求，进入退避，避免只反复调整OCR。
- 优先用已保存失败截图离线验证颜色提取和OCR；截图必须看过后再解释。放大截图的连通域计数不能代表原图计数。诊断完成后用少量未完成票据验证，再续跑单worker批次。

### 中断续跑、健康检查和限流

- `Start-Process` 返回PID只代表创建了进程；本次后台启动后 `/health` 曾连接被拒。须确认 `http://127.0.0.1:<port>/health` 返回 `ok: true`，并查看服务日志；加载模型可能晚于两秒。若后台生命周期不可靠，使用可持续读取输出的执行会话启动服务。
- OCR使用非默认端口时，在查验进程设置 `OCR_URL=http://127.0.0.1:<port>/ocr`，先验证该端口的健康接口。
- 用户中断或切换环境后，原进程可能继续，也可能消失；先续接原执行会话，检查结果文件更新时间及准确的进程命令行。仅看到某个node进程不足以认定它属于查验任务。原进程还在时不要再开worker；原会话不存在且进程确已结束，再恢复OCR并重跑。
- 续跑以 `results.json` 为依据跳过终态；临时失败可自动补验。补充 `checksumCode` 后，“需补充数据”状态现会放行重查。结果保存在原绝对工作目录，切换cwd不会迁移文件；权限变化时先确认目标目录可写。
- 本次串行、票间6–10秒仍多次触发限流，因此旧实测速率只是参考。按提示退避；连续多票验证码未加载时降低请求频率、保留结果，最多追加两轮补验后交付待处理项，避免无限重试。
- 每票每日最多5次；验证码尝试次数与平台实际查验次数不同，记录平台详情中的当日次数，达到上限则次日处理。
